## Архитектура и выбор технологий

### Контекст задачи

Модуль обработки геоданных (Data Processor) решает две ключевые задачи:

1. **Загрузка данных OpenStreetMap** из Overpass API и сохранение в PostgreSQL.
2. **Генерация векторных тайлов (MVT)** в реальном времени для отображения на клиенте (MapLibre GL).

Система должна обеспечивать динамическую настройку уровней детализации (LOD) без перестройки тайлов, поддерживать параллельную загрузку данных и генерировать тайлы с минимальной задержкой.

### Анализ альтернатив

**Таблица: Сравнение подходов к генерации векторных тайлов**

| Подход | Преимущества | Недостатки | Вердикт |
|--------|-------------|-----------|---------|
| **Tippecanoe + статические тайлы** | Высокая скорость отдачи (CDN), предварительная оптимизация | Невозможность динамической LOD, требует пересборки при изменении стилей | ❌ Отклонен |
| **Tileserver GL** | Готовое решение, поддержка MBTiles | Жесткая привязка к формату MBTiles, сложность интеграции с динамическими данными | ❌ Отклонен |
| **Tegola** | Генерация «на лету», поддержка PostGIS | Написан на Go (дополнительная зависимость), ограниченная кастомизация SQL | ⚠️ Рассмотрен |
| **PostgreSQL + ST_AsMVT** | Полный контроль над SQL, нативная интеграция с PostGIS, динамическая LOD | Требует ручной реализации, медленнее статических тайлов | ✅ Выбран |

**Обоснование выбора:**

Выбор PostgreSQL + ST_AsMVT обусловлен требованием динамической настройки LOD. В системе навигации Московской агломерации (МАС) клиент должен иметь возможность изменять видимость типов дорог на разных зумах без пересборки тайлов. Функция `ST_AsMVT` (PostGIS 2.4+) позволяет генерировать MVT-тайлы напрямую из SQL-запроса, что обеспечивает максимальную гибкость фильтрации данных.

Компромисс: генерация «на лету» медленнее предварительно собранных тайлов (50–200 мс vs <10 мс), но избавляет от необходимости хранить терабайты статических файлов и пересобирать их при каждом изменении конфигурации.

### Архитектурный паттерн: On-Demand Generation

Система использует паттерн **On-Demand Generation** (генерация по запросу) вместо традиционного **Pre-Generated Tileset** (предварительная генерация).

```{.mermaid}
sequenceDiagram
    participant Client as MapLibre GL
    participant API as Data Processor API
    participant MVT as MVT Handler
    participant DB as PostgreSQL + PostGIS
    
    Client->>API: GET /tiles/14/9905/5120.mvt
    API->>MVT: generate_tile(z=14, x=9905, y=5120)
    MVT->>MVT: _get_visible_types(z=14) → ['motorway', 'trunk', ...]
    MVT->>DB: SELECT ST_AsMVT(...) WHERE highway = ANY($types)
    DB-->>MVT: MVT bytes (48 KB)
    MVT-->>API: MVT bytes
    API-->>Client: 200 OK, Content-Type: application/vnd.mapbox-vector-tile
```

**Преимущества паттерна:**

- Динамическая LOD: клиент отправляет конфигурацию через WebSocket, сервер сразу применяет её без пересборки.
- Экономия дискового пространства: не нужно хранить тайлы для всех комбинаций зумов и стилей.
- Актуальность данных: изменения в БД сразу отражаются в тайлах.

**Недостатки паттерна:**

- Задержка генерации: 50–200 мс на тайл (зависит от плотности данных).
- Нагрузка на БД: каждый запрос тайла = SQL-запрос с геометрическими операциями.
- Отсутствие кеширования: повторные запросы одного тайла генерируются заново (технический долг).

### Разделение ответственности

Архитектура Data Processor следует принципу **Separation of Concerns** (разделение ответственности). Код разбит на четыре слоя:

**Таблица: Слои архитектуры**

| Слой | Директория | Ответственность | Ключевые файлы |
|------|-----------|----------------|---------------|
| **API Layer** | `src/api/` | HTTP endpoints, валидация запросов, CORS | `tiles.py`, `websocket.py`, `status.py` |
| **Business Logic** | `src/handlers/` | Бизнес-логика (загрузка, генерация MVT, LOD) | `tile_download.py`, `mvt.py`, `utils.py` |
| **Data Access** | `src/db/` | SQL-запросы, пул соединений | `queries.py`, `pool.py` |
| **State Management** | `src/state/` | Управление задачами, прогресс-бар | `task_manager.py` |

**Диаграмма зависимостей:**

```{.mermaid}
graph TD
    A[main.py] --> B[API Layer]
    A --> C[Handlers]
    A --> D[State Manager]
    
    B --> C
    C --> E[Database Layer]
    C --> D
    
    E --> F[PostgreSQL + PostGIS]
    
    B --> G[FastAPI Router]
    C --> H[asyncpg Pool]
    
    style A fill:#e1f5ff
    style B fill:#fff4e1
    style C fill:#e8f5e9
    style D fill:#fce4ec
    style E fill:#f3e5f5
```

**Обоснование разделения:**

- **API Layer** (тонкий слой): только валидация параметров и маршрутизация. Бизнес-логика вынесена в Handlers.
- **Handlers** (толстый слой): вся логика загрузки и генерации. Это позволяет тестировать бизнес-логику независимо от FastAPI.
- **Database Layer**: централизация SQL-запросов в `queries.py` упрощает рефакторинг и предотвращает дублирование кода.
- **State Management**: отдельный модуль для отслеживания прогресса загрузки (используется для UI прогресс-бара в Qt Client).

### Технологический стек

**Таблица: Обоснование выбора технологий**

| Технология | Версия | Обоснование выбора |
|-----------|--------|-------------------|
| **PostgreSQL** | 15 | СУБД с лучшей поддержкой геопространственных данных (PostGIS). Поддержка JSONB для хранения тегов OSM. |
| **PostGIS** | 3.4 | Расширение для геометрических операций. Функция `ST_AsMVT` для генерации MVT-тайлов. |
| **FastAPI** | 0.104 | Асинхронный фреймворк с автоматической генерацией OpenAPI. Поддержка WebSocket. |
| **asyncpg** | 0.29 | Асинхронный драйвер PostgreSQL. Производительность: 7x быстрее psycopg2 при параллельной нагрузке (см. отчет Router). |
| **Python** | 3.11 | Язык с богатой экосистемой геопространственных библиотек (Shapely, Fiona). Поддержка async/await. |
| **Docker** | 24.0 | Контейнеризация для изоляции зависимостей и упрощения развертывания. |

**Конфигурация PostgreSQL:**

Для оптимизации генерации MVT-тайлов используется следующая конфигурация (из `docker-compose.yml`):

```{.yaml caption="docker-compose.yml: конфигурация PostgreSQL"}
postgis:
  image: postgis/postgis:15-3.4
  environment:
    POSTGRES_DB: nav_mas
    POSTGRES_USER: postgres
    POSTGRES_PASSWORD: postgres
  command:
    - "postgres"
    - "-c"
    - "shared_buffers=4GB"
    - "-c"
    - "work_mem=256MB"
    - "-c"
    - "maintenance_work_mem=1GB"
    - "-c"
    - "effective_cache_size=8GB"
  shm_size: 4gb
```

**Обоснование параметров:**

- `shared_buffers=4GB`: кеш данных в памяти. Ускоряет повторные запросы тайлов (холодный старт → горячий кеш).
- `work_mem=256MB`: память для сортировки и JOIN. Критично для `ORDER BY CASE highway` в `GENERATE_MVT_TILE`.
- `effective_cache_size=8GB`: подсказка планировщику о доступной памяти ОС для кеширования.

### Интеграция с Overpass API

Для загрузки данных OpenStreetMap используется Overpass API — публичный сервис для выполнения запросов к базе OSM.

**Таблица: Конфигурация Overpass**

| Параметр | Значение | Обоснование |
|----------|---------|-------------|
| **Серверы** | `overpass-api.de`, `overpass.kumi.systems` | Два зеркала для отказоустойчивости (fallback при 429/503). |
| **Timeout** | 300 секунд | Максимальное время ожидания ответа. Overpass может обрабатывать запрос до 5 минут. |
| **Tile Size** | 0.05° × 0.05° | Размер одного тайла (~5.5 км × 3.7 км на широте Москвы). Компромисс: меньше = больше запросов, больше = риск timeout. |
| **Concurrency** | 5 параллельных запросов | Ограничение Overpass API (rate limiting). Превышение приводит к 429 Too Many Requests. |

**Запрос Overpass QL:**

```{.overpassql caption="Запрос для загрузки дорог в bbox"}
[out:json][timeout:300];
(
  way["highway"](55.70,37.55,55.75,37.60);
);
out geom;
```

**Формат ответа:** JSON с массивом объектов `way`, каждый содержит:
- `id`: OSM ID (уникальный идентификатор).
- `tags`: словарь атрибутов (`highway`, `name`, `maxspeed`, `lanes`, ...).
- `geometry`: массив координат `[lon, lat]`.

### Компромиссы и технический долг

**Таблица: Принятые компромиссы**

| Компромисс | Обоснование | Планы устранения |
|-----------|-------------|------------------|
| **Генерация «на лету» vs кеширование** | Гибкость LOD важнее скорости на текущем этапе. | Добавить Redis для кеширования MVT-тайлов (TTL 1 час). |
| **Отсутствие CDN** | Развертывание в локальной сети (Qt Client на том же хосте). | Интеграция с CloudFlare/Fastly для публичного доступа. |
| **Один источник данных (Overpass)** | Простота интеграции. | Добавить поддержку локальных OSM-файлов (osm2pgsql). |
| **Отсутствие версионирования данных** | YAGNI (You Aren't Gonna Need It) на текущем этапе. | Добавить таблицу `osm.ways_history` для отслеживания изменений. |
