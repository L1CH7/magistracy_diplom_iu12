## Архитектурный контекст и проблематика

### Роль Gateway в микросервисной архитектуре

API Gateway выполняет функцию единой точки входа (Single Entry Point) для клиентских приложений в распределенной системе навигации. Архитектура системы построена по принципу микросервисов, где каждый сервис отвечает за изолированную бизнес-логику:

- **Router Service** (`http://router:8000`): вычисление маршрутов через pgRouting, управление дорожным графом.
- **Data Processor Service** (`http://data-processor:8000`): генерация векторных тайлов (MVT), обработка OSM-данных, WebSocket-уведомления об обновлениях карты.

Gateway скрывает внутреннюю топологию сети от клиента. Клиент взаимодействует только с Gateway (`http://gateway:8000`), который перенаправляет запросы к соответствующим upstream-сервисам. Это обеспечивает:

1. **Изоляцию внутренних сервисов:** Клиент не имеет прямого доступа к Router или Data Processor, что снижает поверхность атаки.
2. **Упрощение клиентской логики:** Клиент не обязан знать URL и порты всех сервисов.
3. **Гибкость масштабирования:** Добавление новых сервисов не требует изменений на стороне клиента.

**Таблица: Маршрутизация запросов через Gateway**

| Клиентский запрос | Upstream-сервис | Внутренний путь |
|-------------------|-----------------|-----------------|
| `GET /tiles/14/1234/5678` | Data Processor | `GET /api/v1/tiles/14/1234/5678` |
| `POST /routing/calculate` | Router | `POST /api/v1/routing/calculate` |
| `GET /graph/status/task-123` | Router | `GET /api/v1/graph/status/task-123` |
| `WS /ws/data_updates` | Data Processor | `WS /ws/data_updates` |

### Проблема жестко закодированных маршрутов

До рефакторинга Gateway использовал декораторы FastAPI для регистрации маршрутов. Каждый эндпоинт описывался отдельной функцией с явным указанием пути и upstream-сервиса:

```{.python caption="Фрагмент legacy кода (до рефакторинга)"}
@app.api_route("/tiles/{path:path}", methods=["GET", "POST", "PUT", "DELETE"])
async def proxy_tiles(request: Request, path: str):
    return await reverse_proxy(request, path, settings.DATA_PROCESSOR_URL, f"/api/v1/tiles/{path}")

@app.api_route("/routing/{path:path}", methods=["GET", "POST", "PUT", "DELETE"])
async def proxy_routing(request: Request, path: str):
    return await reverse_proxy(request, path, settings.ROUTER_URL, f"/api/v1/route/{path}")

@app.api_route("/graph/{path:path}", methods=["GET", "POST", "PUT", "DELETE"])
async def proxy_graph(request: Request, path: str):
    return await reverse_proxy(request, path, settings.ROUTER_URL, f"/api/v1/graph/{path}")
```

Этот подход приводил к следующим проблемам:

1. **Нарушение принципа DRY (Don't Repeat Yourself):** Логика проксирования дублировалась в каждой функции. Изменение алгоритма (например, добавление логирования или обработки ошибок) требовало правки всех функций.

2. **Высокая стоимость добавления новых эндпоинтов:** Для каждого нового пути требовалось писать отдельную функцию, что увеличивало объем кода и риск ошибок.

3. **Жесткая связь с именами переменных:** Использование `settings.DATA_PROCESSOR_URL` и `settings.ROUTER_URL` создавало зависимость от конкретных имен полей в конфигурации. При переходе на централизованную конфигурацию (`services.common.config`) потребовалась бы правка всех функций.

4. **Отсутствие декларативности:** Маршруты были разбросаны по коду. Для понимания полной картины маршрутизации требовалось читать весь файл `main.py` (86 строк до рефакторинга).

### Требования к производительности и безопасности

Gateway работает в критическом пути (critical path) обработки запросов. Каждый запрос клиента проходит через Gateway, поэтому накладные расходы (overhead) Gateway напрямую влияют на общую латентность системы.

**Требования к латентности:**
- **Целевой overhead:** <50 мс на проксирование HTTP-запроса.
- **Целевой overhead WebSocket:** <2 мс на handshake, <1 мс на пересылку сообщения.

Эти требования исключают использование тяжеловесных решений (например, Kong, Envoy) и диктуют выбор легковесного прокси на базе FastAPI + httpx.

**Требования к безопасности:**
- **Базовая защита:** Ограничение доступных эндпоинтов через whitelist в `route_registry.yaml`. Клиент не может обратиться к внутренним эндпоинтам (например, `/api/v1/debug/raw_osm`), если они не зарегистрированы в Gateway.
- **Отсутствие аутентификации:** Осознанный компромисс. Система предназначена для внутреннего использования (закрытая сеть Docker Compose). Добавление JWT-аутентификации увеличило бы overhead на ~10-20 мс (парсинг токена, проверка подписи), что неприемлемо для текущих требований.

**Таблица: Сравнение подходов к Gateway**

| Критерий | Kong / Envoy | Nginx | FastAPI (выбрано) |
|----------|--------------|-------|-------------------|
| Overhead (HTTP) | 20-50 мс | 5-10 мс | 5-10 мс |
| Overhead (WebSocket) | 10-20 мс | 2-5 мс | 2 мс |
| Динамическая конфигурация | Да (Admin API) | Нет (reload required) | Да (Python code) |
| Сложность настройки | Высокая | Средняя | Низкая |
| Интеграция с Python | Плагины (Lua) | Нет | Нативная |

### Обоснование выбора динамической регистрации

Переход на динамическую регистрацию маршрутов через декларативный реестр (`route_registry.yaml`) решает все перечисленные проблемы:

1. **Централизация конфигурации:** Все маршруты описаны в одном файле. Добавление нового эндпоинта требует только правки YAML, без изменений в коде.

2. **Устранение дублирования:** Логика проксирования вынесена в фабрику обработчиков (`create_handler`, `create_root_handler`). Изменение алгоритма требует правки одного места.

3. **Гибкость резолвинга сервисов:** Использование `getattr(settings.services, service_name)` позволяет динамически получать URL сервиса по имени из конфигурации. Это упрощает интеграцию с `services.common.config`.

4. **Декларативность:** Структура маршрутов видна сразу при открытии `route_registry.yaml`. Не требуется анализ кода.

**Пример декларативного описания:**

```{.yaml caption="configs/gateway/route_registry.yaml"}
routes:
  - path: "/tiles"
    service: "data_processor"
    internal_prefix: "/api/v1/tiles"
  
  - path: "/routing"
    service: "router"
    internal_prefix: "/api/v1/routing"
```

Этот подход соответствует принципу **Configuration as Code**, где конфигурация хранится в версионируемом файле и может быть изменена без пересборки Docker-образа.

### Архитектурные паттерны

Gateway реализует следующие паттерны:

1. **API Gateway Pattern:** Единая точка входа для клиентов.
2. **Reverse Proxy Pattern:** Перенаправление запросов к upstream-сервисам с сохранением заголовков и тела запроса.
3. **Registry Pattern:** Централизованное хранилище метаданных маршрутов.
4. **Factory Pattern:** Создание обработчиков через фабричные функции для корректного захвата переменных в замыканиях.

```{.mermaid}
graph TD
    Client[Клиент Qt/Web] -->|HTTP/WS| Gateway[API Gateway]
    Gateway -->|load config| Registry[route_registry.yaml]
    Gateway -->|resolve URL| Settings[services.common.config]
    Gateway -->|proxy HTTP| Router[Router Service]
    Gateway -->|proxy HTTP| DataProc[Data Processor]
    Gateway -->|proxy WS| DataProc
```

### Компромиссы и ограничения

**Отказ от аутентификации:**
- **Причина:** Минимизация overhead. Каждый запрос проходит через Gateway, добавление JWT-проверки увеличило бы латентность на 10-20 мс.
- **Риск:** Система уязвима при развертывании в открытой сети. Требуется внешний firewall или VPN.
- **Митигация:** Использование Docker Compose network isolation. Сервисы доступны только внутри сети `diplom_default`.

**Отсутствие rate limiting:**
- **Причина:** Упрощение архитектуры на этапе MVP. Rate limiting требует хранения состояния (Redis, in-memory cache), что усложняет deployment.
- **Риск:** Возможность DoS-атаки при открытии Gateway наружу.
- **Митигация:** Планируется добавление rate limiting через middleware после интеграции с production-окружением.

**Отсутствие circuit breaker:**
- **Причина:** Простота реализации. Circuit breaker требует отслеживания ошибок upstream-сервисов и временного отключения недоступных сервисов.
- **Риск:** Каскадные сбои при падении upstream-сервиса (все запросы будут ждать timeout 60 сек).
- **Митигация:** Использование короткого timeout (60 сек) и логирования ошибок для мониторинга.
