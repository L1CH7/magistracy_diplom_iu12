## Сравнительный анализ технологий маршрутизации

### Контекст задачи

Перед началом разработки модуля маршрутизации была поставлена задача: обеспечить поиск пути по дорожному графу Московской агломерации (~250,000 ребер) с возможностью динамического изменения весов ребер без перестройки графа. Требование гибкости исключило применение стандартных решений, оптимизированных под статические графы.

### Рассмотренные альтернативы

**Таблица: Сравнение технологий маршрутизации**

| Критерий | OSRM | Valhalla | GraphHopper | Наше решение (pgRouting) |
|----------|------|----------|-------------|--------------------------|
| **Архитектура хранения** | In-Memory (RAM) | MMap Tiles | In-Memory (JVM) | PostgreSQL (Disk + Shared Buffers) |
| **Предобработка графа** | Contraction Hierarchies (CH) | Обязательна | CH / Landmarks | Отсутствует |
| **Время перестройки** | 30-60 мин (Москва) | 20-40 мин | 15-30 мин | Не требуется |
| **Динамическое изменение весов** | Невозможно без rebuild | Ограничено | Невозможно без rebuild | Мгновенно (UPDATE колонки) |
| **Латентность (типичная)** | < 10 мс | 15-30 мс | 20-50 мс | 2500-40000 мс |
| **Потребление RAM** | 4-8 ГБ (граф Москвы) | 2-4 ГБ | 6-12 ГБ (JVM) | 370 МБ (процесс сборки) |
| **Поддержка сложных ограничений** | Фиксированная (C++) | Ограниченная | Средняя (Java) | Произвольная (SQL) |

### Проблема статических движков

OSRM, Valhalla и GraphHopper достигают субсекундной латентности за счет алгоритма Contraction Hierarchies. Суть CH: граф предобрабатывается, создаются "ярлыки" (shortcuts) между удаленными узлами. Это позволяет искать путь не по миллионам ребер, а по тысячам предвычисленных маршрутов.

**Критическое ограничение:** Изменение веса хотя бы одного ребра (например, закрытие улицы на ремонт) требует полной перестройки иерархии. Для графа Москвы это занимает 30-60 минут CPU-времени. Это делает невозможным учет:
- Временных перекрытий дорог (ДТП, мероприятия).
- Динамических штрафов (экологические зоны, платные участки).
- Пользовательских ограничений (избегание определенных районов).

### Выбор: Гибкость вместо скорости

Было принято решение пожертвовать латентностью ради функциональности. PostgreSQL + pgRouting обеспечивают:
1. **Нулевое время перестройки:** Веса ребер хранятся в колонке `cost`. Изменение веса — это обычный `UPDATE`, выполняющийся за миллисекунды.
2. **Произвольная логика:** Любые ограничения реализуются через SQL (`CASE WHEN`, подзапросы, JOIN с внешними таблицами).
3. **Низкое потребление памяти:** Граф на диске, в RAM загружаются только активные участки (через Shared Buffers).

**Компромисс:** Латентность выросла с 10 мс до 2.5-40 секунд. Это приемлемо для логистических систем (планирование маршрутов на день вперед), но неприемлемо для навигаторов реального времени.

## Архитектура решения

### Принцип Database-Centric

Вся графовая математика выполняется внутри PostgreSQL (написан на C, оптимизирован для массовых вычислений). Python-слой (`FastAPI` + `asyncpg`) выступает тонким координатором, отправляющим SQL-запросы и десериализующим результаты.

**Таблица: Распределение ответственности**

| Компонент | Технология | Роль | Обоснование |
|-----------|-----------|------|-------------|
| **API Server** | FastAPI (Python 3.11) | HTTP-интерфейс, валидация запросов | Асинхронная архитектура (`asyncio`) идеальна для I/O-bound задач |
| **Routing Engine** | pgRouting 3.5 | Графовые алгоритмы (Dijkstra, KSP) | Выполнение внутри СУБД экономит сериализацию/десериализацию |
| **СУБД** | PostgreSQL 15 + PostGIS 3.4 | Хранение графа, пространственные индексы | R-Tree (GiST) ускоряет поиск в тысячи раз |
| **Драйвер** | asyncpg | Асинхронное взаимодействие с БД | Бинарный протокол, zero-copy для WKB |

### Поток данных

Система работает в два изолированных этапа:

```{.mermaid}
flowchart TB
    subgraph Build["Этап 1: Построение графа (Build Phase)"]
        OSM[OSM Data] --> DP[Data Processor]
        DP --> |Grid Partitioning| Tiles[Тайлы 0.05°]
        Tiles --> |pgr_nodeNetwork| Topo[Топология]
        Topo --> |Bulk Insert| Graph[(PostgreSQL: graphs.edges)]
    end
    
    subgraph Runtime["Этап 2: Исполнение (Runtime)"]
        Client[HTTP Client] --> API[FastAPI]
        API --> |1. Snap to Node| KNN[KNN Search]
        KNN --> |Node ID| Engine[PgRoutingEngine]
        Engine <--> |SQL: pgr_dijkstra + BBOX| DB[(PostgreSQL)]
        Engine --> |WKB Binary| API
        API --> |JSON| Client
    end
    
    Graph -.->|Read-Only| DB
```

**Критическое разделение:** Build Phase выполняется однократно (или при обновлении карты). Runtime работает с готовым графом в режиме read-only, что позволяет масштабировать чтение горизонтально (read replicas).

## Справочник функций pgRouting

**Таблица: Использованные и отвергнутые алгоритмы**

| Функция | Алгоритм | Статус | Причина решения |
|---------|----------|--------|-----------------|
| `pgr_dijkstra` | Dijkstra (классический) | ✅ Используется | Простота, предсказуемость, отсутствие накладных расходов на эвристику |
| `pgr_astar` | A* (эвристический) | ❌ Отклонен | Вычисление эвристики требует JOIN с `graphs.nodes` на каждой итерации → CPU 100% |
| `pgr_ksp` | Yen's Algorithm (K кратчайших путей) | ❌ Отклонен | Возвращает топологически идентичные пути (разница в 1 сегмент) |
| `pgr_dijkstra` + Iterative Penalty | Кастомный (наш) | ✅ Используется | Обеспечивает реальное разнообразие маршрутов (набережная vs проспект) |

### Почему A* провалился

A* теоретически быстрее Dijkstra за счет направленного поиска. Однако в реляционной СУБД это преимущество нивелируется:

```{.sql caption="Проблемный запрос A* (псевдокод)"}
-- На каждой итерации алгоритма:
SELECT node_id, 
       cost + ST_Distance(current.geom, target.geom) AS f_score
FROM graph_edges
JOIN graph_nodes ON ... -- ← УЗКОЕ МЕСТО
```

Для графа Москвы (250k ребер, ~150k узлов) алгоритм выполняет миллионы JOIN-ов. Профилирование показало: 90% времени уходит на JOIN, 10% — на сам поиск пути.

**Решение:** Отказ от эвристики. Dijkstra с Dynamic BBOX (см. следующий раздел) работает быстрее A* без BBOX.
