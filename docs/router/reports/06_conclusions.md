## Технический долг

### Отказ от pgRouting в пользу C++

**Проблема:** PostgreSQL не предназначен для real-time вычислений. Даже с оптимизациями латентность остается на уровне секунд.

**Решение:** Реализовать собственный движок на C++ с использованием Boost::Graph.

**Преимущества:**
- Граф в RAM (zero I/O).
- Прямой доступ к структурам данных (без SQL overhead).
- Возможность использования Contraction Hierarchies.

**Ожидаемая латентность:** < 50 мс (100x быстрее текущей).

**Статус:** В планах. Требует 2-3 месяца разработки.

### Кэширование "горячих" участков

**Проблема:** Cold Start (40 секунд для первого запроса).

**Решение:** Warm-up скрипт, загружающий центральные районы Москвы в Shared Buffers при старте сервиса.

**Статус:** Концепт описан в Главе 5. Не реализовано.

### Contraction Hierarchies

**Проблема:** Текущий алгоритм (Dijkstra + BBOX) имеет сложность O(E log V). Для больших графов это медленно.

**Решение:** Внедрить Contraction Hierarchies (CH) с поддержкой динамических весов.

**Сложность:** CH требует предобработки, но можно реализовать "частичную" CH: предобработать магистрали (МКАД, ТТК), оставив локальные дороги динамическими.

**Статус:** Исследовательская задача.

## Интеграция с МАС (Мультиагентная Система)

### Требования МАС к роутеру

Будущая МАС будет координировать движение тысяч агентов (роботов, дронов). Требования:
1. **Латентность:** < 100 мс (текущая: 6000 мс).
2. **Throughput:** 10,000 запросов/сек (текущая: ~200 запросов/сек).
3. **Headless режим:** Без UI-фич (K-маршруты не нужны).

### Архитектурная готовность

**Текущее разделение:**
- `find_route(start, end)` — ядро для МАС (оптимизировано).
- `find_k_routes(start, end, k)` — UI-слой (можно удалить).

**План миграции:**
1. Вынести `find_k_routes` в отдельный сервис (BFF — Backend for Frontend).
2. Переписать `find_route` на C++ (см. выше).
3. Развернуть роутер как gRPC-сервис (вместо HTTP REST).

**Статус:** Архитектура готова к разделению. Требуется реализация.

## Расширение функциональности

### Мультимодальные маршруты

**Задача:** Учет общественного транспорта (метро, автобусы).

**Подход:** Создать "виртуальные" ребра между остановками транспорта. Вес ребра = время ожидания + время в пути.

**Сложность:** Требуется интеграция с расписаниями (GTFS).

**Статус:** Не реализовано.

### Учет пробок (динамические веса)

**Задача:** Изменять веса ребер в зависимости от текущей загрузки дорог.

**Подход:** Интеграция с API Яндекс.Пробки или собственная система мониторинга.

**Реализация:**

```{.sql caption="Обновление весов на основе пробок"}
UPDATE graphs.edges
SET cost = base_cost * traffic_multiplier
WHERE id IN (SELECT edge_id FROM traffic_data WHERE congestion > 0.7);
```

**Статус:** Архитектура поддерживает (это просто UPDATE), но источник данных отсутствует.

### Turn Restrictions (ограничения поворотов)

**Задача:** Учет запретов поворотов (например, "нельзя повернуть налево с Тверской на Моховую").

**Подход:** Использовать `pgr_dijkstra` с параметром `cost_turn`:

```{.sql caption="Учет штрафов за повороты"}
SELECT * FROM pgr_dijkstra(
    'SELECT id, source, target, cost, reverse_cost FROM edges',
    start, end,
    directed := true,
    cost_turn := 'SELECT * FROM turn_restrictions'
);
```

**Статус:** pgRouting поддерживает, но данные OSM не содержат полной информации о поворотах для Москвы.

### Границы применимости

**Подходит для:**
- Логистических систем (планирование маршрутов доставки).
- Диспетчерских служб (координация транспорта).
- Аналитики (постобработка данных).

**НЕ подходит для:**
- Навигаторов реального времени (требуется < 100 мс).
- Игровых систем (требуется < 16 мс).
- High-Frequency систем (требуется < 1 мс).

### Ключевые компромиссы

**Таблица: Trade-offs**

| Решение | Плюс | Минус |
|---------|------|-------|
| PostgreSQL вместо In-Memory | Гибкость, низкое потребление RAM | Высокая латентность (I/O) |
| Dijkstra вместо A* | Простота, предсказуемость | Нет эвристики (но BBOX компенсирует) |
| Iterative Penalty вместо KSP | Реальное разнообразие маршрутов | Линейный рост времени с K |
| Grid Partitioning | Решение OOM | Усложнение процесса сборки |

### Честная самооценка

**Что сделано хорошо:**
1. Решена критическая проблема OOM (12 ГБ → 370 МБ).
2. Достигнута стабильность (100% success для K=1).
3. Архитектура готова к интеграции с МАС.

**Что можно улучшить:**
1. Латентность остается высокой (6 сек vs 10 мс у OSRM).
2. Cold Start не устранен (40 сек для первого запроса).
3. Отсутствует кэширование и Warm-up.

**Главный вывод:** Мы построили систему, которая жертвует скоростью ради гибкости. Это осознанный компромисс, оправданный требованиями задачи (динамические веса, сложные ограничения). Для сценариев, где латентность критична, требуется переход на C++ + In-Memory архитектуру.
