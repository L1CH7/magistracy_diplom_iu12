## Методология тестирования

### Отказ от синтетических тестов

Стандартный подход к бенчмаркингу: создать искусственный граф (решетка, дерево) и измерить скорость на нем. Такие тесты дают красивые графики, но не отражают реальность.

**Наш подход:** Использовать реальную карту Москвы и случайные пары точек.

**Генерация тестовых данных:**

```{.python caption="Генератор случайных маршрутов"}
import random
from shapely.geometry import Point, box

# BBOX Москвы (приблизительно)
moscow_bbox = box(37.3, 55.5, 37.9, 55.9)

test_cases = []
for _ in range(1000):
    origin = Point(
        random.uniform(37.3, 37.9),
        random.uniform(55.5, 55.9)
    )
    destination = Point(
        random.uniform(37.3, 37.9),
        random.uniform(55.5, 55.9)
    )
    test_cases.append((origin, destination))
```

Это дает распределение маршрутов от коротких (внутри района, 1-2 км) до длинных (Химки → Бутово, 30+ км).

### Разбор: Куда уходят 6 секунд?

Если алгоритм Dijkstra работает за O(E log V) и граф в памяти, почему пользователь ждет 6 секунд?

**Профилирование запроса** (EXPLAIN ANALYZE):

```{.sql caption="Типичный запрос с профилированием"}
EXPLAIN (ANALYZE, BUFFERS) 
SELECT * FROM pgr_dijkstra(...);
```

**Результат:**

| Этап | Время (мс) | Доля | Описание |
|------|------------|------|----------|
| **Disk I/O** | 5800 | 93% | Чтение ребер с диска (NVMe SSD) |
| **Index Scan (GiST)** | 320 | 5% | Поиск по пространственному индексу |
| **Dijkstra (CPU)** | 80 | 1.3% | Сам алгоритм поиска пути |
| **Geometry Decode (WKB)** | 50 | 0.7% | Десериализация бинарных данных |

**Вывод:** Система **I/O Bound** (упирается в диск), а не CPU Bound.

### Феномен Cold Start

**Определение:** Первый запрос к участку графа, который давно не запрашивался, занимает до 40 секунд. Повторный запрос к тому же участку — 2.5 секунды.

**Причина:** PostgreSQL использует Shared Buffers (кэш в RAM). Если данные не в кэше, они читаются с диска:

1. **Seek Time:** Позиционирование головки диска (даже на SSD: ~0.1 мс на блок).
2. **Read Time:** Чтение блоков данных (NVMe: ~500 МБ/с).
3. **Parse Time:** Разбор структуры страниц PostgreSQL.

Для графа Москвы (244k ребер × ~500 байт/ребро ≈ 120 МБ) первое чтение занимает ~6 секунд.

**Повторный запрос:** Данные уже в Shared Buffers → чтение из RAM (~20 ГБ/с) → 2.5 секунды.

**Стратегия оптимизации (не реализована):** Warm-up скрипт, который загружает "горячие" участки графа (центр Москвы) в кэш при старте сервиса.

### Объяснение: MVCC и Асинхронность

PostgreSQL использует **MVCC (Multiversion Concurrency Control)**: каждый запрос видит "снимок" данных на момент начала транзакции. Это позволяет читающим запросам не блокировать друг друга.

**Архитектура взаимодействия:**

```{.mermaid}
sequenceDiagram
    participant C1 as Client 1
    participant C2 as Client 2
    participant API as FastAPI (asyncio)
    participant PG as PostgreSQL
    
    C1->>API: GET /route?from=A&to=B
    C2->>API: GET /route?from=C&to=D
    
    API->>PG: Query 1 (async)
    API->>PG: Query 2 (async)
    
    Note over PG: MVCC: Queries don't block each other
    
    PG-->>API: Result 1 (WKB)
    PG-->>API: Result 2 (WKB)
    
    API-->>C1: JSON Response
    API-->>C2: JSON Response
```

**Ключевой момент:** Пока один процесс ждет I/O (чтение с диска), CPU переключается на другой запрос. Это обеспечивает высокую утилизацию ресурсов.

**Измеренная утилизация CPU:**
- 1 воркер: 12% CPU (ожидание I/O).
- 16 воркеров: 87% CPU (эффективная параллелизация).

## Анализ качества маршрутов

### Успешность поиска (Yield Rate)

**Определение:** Процент запросов, для которых удалось найти маршрут.

**Результаты тестирования:**

**Таблица: Yield Rate по сложности запроса**

| N (точек) | K=1 | K=2 | K=3 | K=5 |
|-----------|-----|-----|-----|-----|
| 2 | 100% | 98% | 94% | 87% |
| 3 | 100% | 96% | 89% | 72% |
| 4 | 100% | 93% | 81% | 58% |
| 5 | 100% | 88% | 69% | 41% |

**Анализ:**

1. **K=1 (100%):** После исправления SQL-синтаксиса (двойной `%%` → `%`) поиск одного маршрута работает безотказно.
2. **Падение для K>1:** С ростом K и N вероятность найти уникальные маршруты падает. Это **физическое ограничение топологии**, а не ошибка алгоритма.

**Пример:** Для маршрута через 5 точек (A → B → C → D → E → F) граф дорог может не иметь 5 *независимых* путей. Особенно если точки расположены на одной магистрали.

## Регрессионный анализ

### Зависимость от сложности

**Гипотеза:** Время поиска линейно зависит от сложности задачи $C = N \times K$, где:
- $N$ — количество точек маршрута.
- $K$ — количество альтернатив.

**Модель:**

$$
T = k \cdot C + b
$$

**Результаты линейной регрессии:**

| Параметр | Значение | Интерпретация |
|----------|----------|---------------|
| $k$ (slope) | 1.23 сек/единицу | Каждая дополнительная итерация добавляет ~1.2 сек |
| $b$ (intercept) | 4.1 сек | Базовая задержка (I/O, парсинг) |
| $R^2$ | 0.61 | Коэффициент детерминации |

**Анализ $R^2 = 0.61$:**

В синтетических тестах (искусственный граф, без I/O) $R^2$ был 0.85. Снижение до 0.61 объясняется "шумом" реальной среды:
- **I/O вариативность:** Cold Start vs Hot Cache (2.5 сек vs 40 сек).
- **Garbage Collection:** Python GC срабатывает непредсказуемо.
- **Сетевые задержки:** HTTP overhead, сериализация JSON.

**Вывод:** Модель корректна, но реальная система имеет высокую дисперсию из-за внешних факторов.
