### 📋 Промпт для составления отчета (Technical Report Summary)

**Контекст:**
Мы разрабатываем высоконагруженный движок маршрутизации для Москвы (250k+ ребер) на базе PostgreSQL/PostGIS + Python.

**1. Оптимизация построения графа (Build Phase)**

* **Проблема:** Стандартная функция `pgr_nodeNetwork` потребляла >12GB RAM, вызывала OOM (Out Of Memory) и зависала на часами из-за огромных геометрий (МКАД ~8км одним куском) и неэффективной работы с памятью.
* **Решение 1 (Geometry Prep):** Внедрена двухэтапная нарезка геометрии перед загрузкой.
* `ST_Segmentize(50m)`: Принудительное добавление вершин каждые 50м.
* `ST_Subdivide(20 vertices)`: Физическая нарезка линий на сегменты <1км.


* **Решение 2 (Grid Strategy):** Полный отказ от `pgr_nodeNetwork` в пользу кастомного Python-скрипта с алгоритмом **"Grid Partitioning" (Плиточная нарезка)**.
* Карта разбивается на сетку 0.05 градуса (~5км).
* Топология строится (noding) итеративно для каждой плитки в отдельной транзакции.
* Используется `ST_UnaryUnion` + `ST_SnapToGrid` для разрешения пересечений.


* **Результат:**
* Потребление RAM упало с **>10GB до 370MB** (стабильная полка).
* Время построения графа (Step 2) сократилось с "бесконечности/зависания" до **~9 минут**.
* Полный успех на слабом железе (Docker с ограничением памяти).



**2. Оптимизация Runtime-роутинга (High-Load 50+ threads)**

* **Проблема:** Исходный A* (`pgr_astar`) использовал фиксированный буфер поиска (11км), тяжелые `JOIN` с таблицей узлов и медленный формат GeoJSON. Это убивало CPU при конкурентных запросах.
* **Решение 1 (Dynamic BBOX):** Переход на `pgr_dijkstra` с динамическим окном поиска: `Buffer = Distance * 2.0` (минимум ~2км). Для коротких маршрутов граф загружается мгновенно.
* **Решение 2 (Binary Protocol):** Замена `ST_AsGeoJSON` на **WKB (`ST_AsBinary`)**. Парсинг геометрии перенесен в Python (`shapely.wkb`), что сняло нагрузку на форматирование текста с БД.
* **Решение 3 (SQL Optimization):** Удалены лишние `JOIN graphs.nodes` из внутреннего запроса роутинга.

**3. Исправление качества данных (Data Quality & UX)**

* **Fix "Zig-Zag" Artifacts:** Исправлен баг визуализации, когда линии рисовались в обратную сторону. Внедрена проверка направления: `CASE WHEN node = source_id THEN geom ELSE ST_Reverse(geom)`.
* **Smart Snapping:** Заменен поиск ближайшего ребра (который "магнитил" к перпендикулярным улицам) на поиск ближайшего **Узла Графа (Vertex)** через пространственный индекс (`<->` operator на `graphs.nodes`).
* **Alternative Routes (Iterative Penalty):** Заменен алгоритм Йена (`pgr_ksp`), который выдавал одинаковые маршруты. Реализована стратегия **Iterative Penalty Dijkstra**:
1. Найти лучший путь.
2. Повысить стоимость (Cost) пройденных ребер в 5 раз.
3. Найти новый путь (алгоритм вынужден искать другую улицу).
4. Результат: Реально разнообразные маршруты.



**Итог:**
Система переведена из состояния "Прототип, падающий по OOM" в состояние "Production-Ready решение", способное выдержать стресс-тест в 50 потоков, с оптимизированной памятью и качественной геометрией.
