# ВВЕДЕНИЕ

Городская навигация в современных условиях транспортных заторов требует перехода от классических алгоритмов поиска единственного кратчайшего пути (алгоритм Дейкстры, A*) к системам, способным предоставлять альтернативные маршруты с учётом текущей загрузки дорог. Рост плотности городского транспорта делает неэффективным использование статических моделей маршрутизации, предполагающих постоянную скорость движения по участкам. Водители сталкиваются с ситуацией, когда формально кратчайший маршрут оказывается медленнее объездных путей из-за пробок на магистральных дорогах.

Задача поиска k кратчайших путей позволяет предоставить пользователю набор различающихся маршрутов, отсортированных по времени прохождения, из которых он может выбрать вариант с учётом личных предпочтений (избежание платных дорог, выбор более живописного маршрута). Алгоритм Йена, реализованный в библиотеке pgRouting как функция `pgr_KSP`, обеспечивает эффективное нахождение k путей без дублирования и с гарантией оптимальности.

Динамическая загрузка дорожной сети моделируется через функцию задержки BPR (Bureau of Public Roads), учитывающую соотношение текущего потока к пропускной способности участка. Модель BPR, изначально разработанная для макроскопического моделирования транспортных потоков, демонстрирует применимость в мультиагентных системах для оценки влияния одновременного движения агентов на время прохождения участков дорог. Пропускная способность вычисляется на основе физических параметров дороги (количество полос, длина, допустимая скорость) и характеристик транспортного средства (длина автомобиля, безопасная дистанция).

Использование данных OpenStreetMap обеспечивает доступ к актуальной детальной информации о дорожной сети для любого региона мира, включая атрибуты дорог (количество полос, одностороннее движение, ограничения скорости), геометрию путей в формате WGS 84, ограничения поворотов, барьеры. Формат Mapbox Vector Tiles (MVT) обеспечивает эффективную передачу векторной геометрии для интерактивного рендеринга в веб-браузере с поддержкой масштабирования и стилизации на клиентской стороне. Функция PostGIS `ST_AsMVT` позволяет генерировать MVT тайлы непосредственно в базе данных без промежуточного сериализационного слоя.

Система логирования на основе библиотеки Loguru с записью структурированных логов в формате JSON Lines обеспечивает возможность анализа производительности и диагностики проблем в распределённой системе. Grafana используется для визуализации метрик и состояния системы, обеспечивая оперативное обнаружение аномалий и узких мест.

**Цель работы** — разработать программную систему мультиагентной навигации с поддержкой альтернативных маршрутов на основе алгоритма pgr_KSP, учитывающую динамическую загрузку дорог через модель BPR, использующую актуальные данные OpenStreetMap и обеспечивающую векторную визуализацию через Mapbox Vector Tiles.

**Для достижения цели необходимо решить следующие задачи:**

1. **Анализ структуры данных OpenStreetMap**. Исследование форматов хранения OSM (XML, PBF, Overpass JSON), изучение тегов для дорожных объектов (highway, lanes, oneway, maxspeed), механизмов представления геометрии путей, ограничений поворотов и барьеров.

2. **Проектирование схемы базы данных PostgreSQL/PostGIS**. Разработка схемы osm для хранения сырых данных (таблицы ways, nodes, barriers, turn_restrictions), схемы graphs для топологического графа (таблицы nodes, edges с генерируемыми полями cost/reverse_cost), создание триггеров для автоматического вычисления атрибутов рёбер (длина, пропускная способность, cost на основе BPR).

3. **Реализация алгоритма построения графа из данных OSM**. Разработка модуля обнаружения пересечений путей средствами PostGIS (`ST_Intersects`, `ST_Intersection`), сегментации путей на рёбра графа функцией `ST_LineSubstring`, создания узлов графа в точках пересечений и концов путей, индексации пространственных данных через GiST.

4. **Интеграция модели пропускной способности и функции задержки BPR**. Разработка формулы вычисления capacity на основе физических параметров (длина, количество полос, допустимая скорость, безопасная дистанция), реализация функции BPR в генерируемых полях PostgreSQL для динамического вычисления cost с учётом current_load.

5. **Реализация маршрутизации с использованием pgr_KSP**. Интеграция функции pgRouting pgr_KSP для поиска k альтернативных маршрутов, разработка API эндпоинта для запроса маршрутов с параметрами start_lon/start_lat, end_lon/end_lat, k, реализация механизма снэппинга координат к ближайшим узлам графа через `ST_Distance`.

6. **Реализация микросервисной архитектуры**. Разработка сервисов: data-processor (загрузка OSM из Overpass API, генерация MVT тайлов функцией `ST_AsMVT`), router (построение графа, маршрутизация через pgr_KSP), gateway (точка входа для клиентов, проксирование запросов к data-processor и router).

7. **Разработка графического клиента**. Реализация GUI приложения на PyQt5 с интеграцией MapLibre GL JS для векторного рендеринга карт, отображения альтернативных маршрутов разными цветами, интерактивного выбора точек начала и конца маршрута на карте.

8. **Организация инфраструктуры Docker Compose**. Конфигурация 5 сервисов (postgis, data-processor, router, gateway, grafana), настройка healthchecks для обеспечения корректной последовательности запуска, монтирование томов для персистентности данных (postgis_data, grafana_data), организация bridge сети для взаимодействия контейнеров.

9. **Интеграция системы логирования Loguru**. Настройка структурированного логирования в JSON Lines формат, конфигурация ротации логов и уровней логирования (DEBUG, INFO, WARNING, ERROR), разработка единого формата логов для всех сервисов с контекстными полями (service, request_id, agent_id).

10. **Экспериментальное исследование производительности**. Измерение времени построения графа на реальных данных OpenStreetMap для г. Москвы, оценка времени маршрутизации pgr_KSP в зависимости от параметра k, анализ времени генерации MVT тайлов на различных уровнях масштабирования, измерение потребления ресурсов Docker контейнеров.

Научная новизна работы заключается в интеграции алгоритма pgr_KSP для поиска k альтернативных путей с моделью динамической загрузки BPR, вычисляемой через генерируемые поля PostgreSQL, что обеспечивает автоматический пересчёт стоимости рёбер при изменении загрузки без необходимости инвалидации кэша маршрутов. Практическая значимость подтверждается разработкой микросервисной архитектуры с использованием современного стека технологий (PostgreSQL 17, PostGIS 3.5, pgRouting 3.8, asyncpg, FastAPI, Docker Compose), обеспечивающей масштабируемость и воспроизводимость окружения.

Структура отчёта соответствует логике решения поставленных задач:

**Раздел 1 "Постановка задачи и требования"** содержит детальное обоснование необходимости разработки системы, сравнительный анализ существующих подходов к навигации (Dijkstra, A*, Contraction Hierarchies, Time-Dependent Routing), формулировку функциональных требований (поддержка альтернативных маршрутов, учёт загрузки дорог, векторная визуализация) и нефункциональных требований (производительность маршрутизации <1000 мс, генерация MVT тайлов <100 мс, потребление памяти <2 ГБ).

**Раздел 2 "Исследование структуры данных OpenStreetMap и формата MVT"** посвящён анализу модели данных OSM. Подробно рассмотрены элементы node, way, relation, теги дорожных объектов (13 категорий highway от motorway до living_street), механизмы хранения геометрии через последовательности узлов, ограничения поворотов через relation типа restriction. Описан формат Mapbox Vector Tiles: структура Protocol Buffers сообщений, кодирование геометрии через delta-encoding, LOD система из 4 слоёв (highways, major_roads, arterial_roads, all_roads), функция PostGIS `ST_AsMVT` для генерации тайлов.

**Раздел 3 "Проектирование базы данных PostgreSQL/PostGIS"** описывает многослойную архитектуру базы данных с двумя схемами: osm (сырые данные из Overpass API), graphs (топологический граф для маршрутизации). Приведена ER-диаграмма с таблицами osm.ways, osm.nodes, osm.barriers, osm.turn_restrictions, graphs.nodes, graphs.edges. Детально рассмотрены 24 атрибута таблицы graphs.edges (source, target, length_m, lanes, oneway, maxspeed, highway, capacity, cost, reverse_cost, current_load, geom), триггеры для автоматического вычисления атрибутов, индексы GiST для пространственных запросов.

**Раздел 4 "Реализация программных модулей системы"** содержит описание микросервисной архитектуры системы. Детально рассмотрены сервисы data-processor (загрузка OSM через Overpass API с fallback на альтернативные серверы, генерация MVT тайлов функцией `ST_AsMVT`, управление фоновыми задачами), router (построение графа через процедуру build_graph(), маршрутизация pgr_KSP, снэппинг координат к узлам), gateway (проксирование запросов от клиентов к data-processor и router). Приведена реализация GUI клиента на PyQt5 с интеграцией MapLibre GL JS для векторного рендеринга карт.

**Раздел 5 "Инфраструктура разработки и эксплуатации системы"** посвящён организации контейнерной инфраструктуры Docker Compose. Описаны конфигурации 5 сервисов (postgis, data-processor, router, gateway, grafana), healthchecks для контроля состояния сервисов, тома для персистентности данных (postgis_data, grafana_data), сетевая конфигурация bridge типа nav-net. Представлена система логирования Loguru с записью структурированных логов в JSON Lines формат, конфигурация Grafana для визуализации метрик. Описана система конфигурации на основе YAML с поддержкой директивы `!include` для композиции конфигурационных файлов, Git workflow с feature branch моделью.

**Раздел 6 "Экспериментальное исследование производительности"** содержит результаты тестирования системы на реальных данных OpenStreetMap для региона moscow_center (44 821 дорожных путей, 59 099 узлов графа, 72 309 рёбер графа). Представлены измерения времени построения графа (~30 секунд), маршрутизации pgr_KSP для k=3 альтернативных маршрутов (241.0 мс), генерации MVT тайла на масштабе z=14 (15.2 мс). Проанализировано потребление ресурсов Docker контейнеров в idle режиме (256 МБ) и под нагрузкой (~1 ГБ). Выявлены ограничения системы и предложены направления дальнейшего развития.

**Заключение** обобщает достигнутые результаты исследования, подтверждает выполнение всех поставленных задач с соблюдением требований производительности, перечисляет направления дальнейшей работы (интеграция pgr_trsp для учёта ограничений поворотов, оптимизация построения графа через пространственное разбиение, интеграция внешних источников трафика, масштабирование через горизонтальное scaling сервисов).
