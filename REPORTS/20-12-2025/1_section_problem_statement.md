# 1 ПОСТАНОВКА ЗАДАЧИ И ТРЕБОВАНИЯ К СИСТЕМЕ

## 1.1 Актуальность и проблематика маршрутизации на динамическом графе

Современные навигационные системы сталкиваются с необходимостью обработки больших объемов пространственных данных в режиме реального времени. Классические подходы к маршрутизации, основанные на статических графах дорожной сети, не учитывают динамически изменяющуюся загрузку транспортной инфраструктуры. Задача построения оптимального маршрута осложняется необходимостью учета пробок, дорожных работ, временных ограничений движения и других факторов, влияющих на время прохождения участков сети.

В рамках настоящего исследования была поставлена задача разработки программного комплекса для маршрутизации на динамическом графе дорожной сети с использованием открытых геопространственных данных OpenStreetMap (OSM). Актуальность работы определяется следующими факторами:

1. **Масштабируемость обработки геоданных**. Существующие коммерческие решения (Google Maps API, HERE Technologies) предоставляют доступ к маршрутизации через проприетарные API с ограничениями на количество запросов и отсутствием возможности модификации алгоритмов. Открытые решения на основе OSM (OSRM, GraphHopper, Valhalla) предназначены преимущественно для статической маршрутизации и не предоставляют встроенных механизмов моделирования динамической загрузки сети.

2. **Интеграция пространственных СУБД**. Использование специализированных расширений PostgreSQL (PostGIS для геометрических операций, pgRouting для графовых алгоритмов) позволяет реализовать единое хранилище данных дорожной сети с поддержкой сложных пространственных запросов, индексации географических объектов и встроенных функций маршрутизации. Данный подход обеспечивает консистентность данных и упрощает интеграцию с внешними системами мониторинга транспортных потоков.

3. **Векторные тайлы для визуализации**. Классические растровые тайловые системы (используемые в OSM Tile Servers, Mapbox Raster Tiles) требуют предварительного рендеринга изображений для каждого уровня масштабирования, что создает высокую нагрузку на хранилище и ограничивает возможности стилизации на стороне клиента. Формат Mapbox Vector Tiles (MVT) предоставляет компактное представление геометрии в бинарном формате Protocol Buffers с поддержкой динамического рендеринга средствами WebGL в браузере клиента.

4. **Моделирование транспортных потоков**. Для учета динамической загрузки дорожной сети требуется механизм оценки пропускной способности ребер графа и влияния загрузки на время прохождения. Классическая функция задержки Bureau of Public Roads (BPR) позволяет моделировать зависимость скорости движения от текущей загрузки относительно максимальной пропускной способности участка.

Задача исследования заключается в проектировании и реализации программного комплекса, обеспечивающего:
- Загрузку и структурированное хранение данных дорожной сети из OSM Overpass API;
- Построение графа дорожной сети с учетом топологических связей, ограничений движения (turn restrictions), барьеров и односторонних участков;
- Генерацию векторных тайлов формата MVT для визуализации карты в клиентском приложении;
- Реализацию алгоритмов поиска k-кратчайших путей с использованием библиотеки pgRouting;
- Динамическую оценку стоимости ребер графа на основе функции BPR с учетом текущей загрузки;
- Структурированное логирование событий системы и интеграцию с системой визуализации метрик Grafana.

## 1.2 Ограничения открытых данных и принятые допущения

Использование открытых геопространственных данных OSM накладывает ряд ограничений на точность и полноту информации о дорожной сети:

1. **Неполнота атрибутивных данных**. Значительная часть дорожных сегментов в OSM не содержит информации о скоростных ограничениях (`maxspeed`), количестве полос движения (`lanes`), типе покрытия (`surface`) и других параметрах, влияющих на оценку времени прохождения участка. В рамках исследования были приняты следующие допущения:
   - Скоростной режим определяется по типу дороги (`highway` tag) с использованием справочных значений из конфигурационного файла `configs/router_config.yaml`;
   - Количество полос по умолчанию принято равным 1 для дорог категорий `residential`, `service`, `unclassified`;
   - Пропускная способность участка рассчитывается по формуле: `capacity = (length_m * lanes) / (avg_vehicle_length + safe_distance)`, где `avg_vehicle_length = 4.5 м`, `safe_distance = v × 2 с` (правило двух секунд).

2. **Противоречивость геометрических данных**. В OSM встречаются случаи пересечения дорожных сегментов без явного указания узла пересечения, что приводит к топологическим ошибкам графа. Для устранения данной проблемы была реализована процедура `find_and_create_intersection_nodes()` в модуле `services/router/src/graph/graph_builder.py`, выполняющая автоматическое обнаружение пересечений средствами PostGIS (`ST_Intersection`) и создание узлов графа в точках пересечения с последующей сегментацией дорожных путей функцией `ST_LineSubstring`.

3. **Отсутствие данных о реальной загрузке**. OSM не содержит информации о текущей интенсивности транспортных потоков. В рамках исследования реализован механизм динамического обновления загрузки ребер графа полем `current_load` в таблице `graphs.edges`. Значение загрузки обновляется по мере прохождения маршрутов агентами в симуляции, что позволяет моделировать влияние пробок на время прохождения участков. Данный подход является упрощением реальной модели транспортных потоков и не учитывает внешние факторы (светофоры, дорожно-транспортные происшествия, метеоусловия).

4. **Ограничения Overpass API**. Сервис Overpass API накладывает ограничения на размер географической области запроса и частоту обращений. Для оптимизации загрузки данных была реализана система тайлового кэширования в таблице `osm.cached_tiles`, предотвращающая повторную загрузку ранее обработанных участков. Геометрия запроса автоматически обрезается по границам предустановленного региона (определяется в файле `configs/bboxes.yaml`) для предотвращения загрузки избыточных данных за пределами исследуемой территории.

5. **Точность координат и погрешности снаппинга**. Координаты узлов дорожной сети хранятся в системе координат WGS84 (EPSG:4326) с точностью до 7 знаков после десятичной точки (~1 см на экваторе). При построении графа выполняется снаппинг узлов к регулярной сетке функцией `ST_SnapToGrid(geom, 0.00001)` для объединения близко расположенных точек пересечений. Толеранс снаппинга составляет 0.00001° (~0.7 м на широте Москвы 55°), что соответствует точности позиционирования GPS-приемников класса Automotive.

Принятые допущения позволяют обеспечить работоспособность системы при неполноте исходных данных, однако ограничивают точность оценки времени прохождения маршрута. Для повышения точности в перспективе планируется интеграция с внешними источниками данных о транспортной ситуации (Yandex Maps Traffic API, HERE Traffic API, TomTom Traffic API).

## 1.3 Цель и задачи исследования на текущем этапе

**Цель исследования**: разработка программного комплекса для маршрутизации транспортных средств на динамическом графе дорожной сети с использованием открытых геопространственных данных и пространственной СУБД PostgreSQL/PostGIS/pgRouting.

**Задачи исследования**:

1. **Анализ структуры данных OpenStreetMap**. Исследование схемы тегирования дорожных объектов OSM, выявление критически важных атрибутов (`highway`, `oneway`, `maxspeed`, `lanes`, `access`, `barrier`), изучение формата JSON-ответов Overpass API. Разработка спецификации минимального набора тегов, необходимых для построения корректного графа маршрутизации.

2. **Проектирование схемы базы данных**. Разработка многослойной архитектуры хранилища с разделением на схему `osm` (сырые данные OSM в первоначальном виде) и схему `graphs` (обработанный граф дорожной сети с узлами, ребрами, дорожными ограничениями). Определение структуры таблиц, индексов, триггеров, хранимых функций PostGIS/pgRouting.

3. **Реализация алгоритма построения графа**. Разработка модуля `GraphBuilder` для преобразования OSM-путей (ways) в рёбра графа с автоматическим обнаружением узлов пересечений, сегментацией длинных дорожных участков, вычислением геометрических атрибутов (длина, начальный/конечный азимут), заполнением скоростных характеристик и пропускной способности.

4. **Интеграция библиотеки pgRouting**. Реализация модуля `PgRoutingEngine` для выполнения запросов к функциям pgRouting (`pgr_KSP` для поиска k-кратчайших путей, `pgr_connectedComponents` для анализа связности графа). Разработка механизма извлечения геометрии маршрута из последовательности ребер с учетом направления траверса (прямое или обратное).

5. **Реализация модели динамической стоимости рёбер**. Внедрение функции задержки BPR в виде генерируемых полей `cost` и `reverse_cost` таблицы `graphs.edges`. Разработка механизма динамического обновления загрузки ребер при прохождении маршрутов агентами.

6. **Разработка сервиса предварительной обработки данных**. Реализация микросервиса `data-processor` на базе FastAPI для загрузки данных из Overpass API, генерации векторных тайлов формата MVT функцией `ST_AsMVT`, управления кэшем загруженных тайлов.

7. **Разработка сервиса маршрутизации**. Реализация микросервиса `router` на базе FastAPI для обработки запросов на построение маршрутов, управления графом дорожной сети (пересборка графа, анализ связности), экспорта данных графа в формате GeoJSON.

8. **Реализация графического клиента**. Разработка десктопного приложения на PyQt5 с интеграцией библиотеки MapLibre GL JS для рендеринга векторной карты средствами WebGL. Реализация механизма загрузки векторных тайлов через HTTP API, отображения маршрутов, интерактивного выбора точек старта/финиша на карте.

9. **Организация инфраструктуры**. Контейнеризация всех сервисов средствами Docker Compose, настройка системы структурированного логирования на базе Loguru, интеграция с системой сбора логов Grafana Loki и визуализации метрик Grafana.

10. **Экспериментальное исследование производительности**. Проведение измерений времени загрузки данных из Overpass API, времени построения графа для регионов различной площади (moscow_center, moscow_mkad), времени выполнения запросов маршрутизации pgRouting. Анализ влияния параметра `k` (количество альтернативных маршрутов) на время выполнения запроса `pgr_KSP`.

## 1.4 Функциональные и нефункциональные требования

### 1.4.1 Функциональные требования

**FR-1. Загрузка данных дорожной сети**
- Система должна обеспечивать загрузку данных дорожной сети из Overpass API для произвольной географической области, заданной ограничивающим прямоугольником (bounding box).
- Система должна автоматически обрезать запрашиваемую область по границам предустановленного региона (определяется в конфигурации `bboxes.yaml`).
- Система должна кэшировать загруженные тайлы для предотвращения повторных запросов к Overpass API.

**FR-2. Построение графа дорожной сети**
- Система должна автоматически строить граф дорожной сети из загруженных OSM-данных с созданием узлов в точках пересечений и концах дорожных сегментов.
- Система должна выполнять сегментацию длинных дорожных путей (OSM ways) на отдельные рёбра графа в местах пересечений с другими путями.
- Система должна корректно обрабатывать односторонние участки дорог (тег `oneway=yes`), устанавливая `reverse_cost = -1` для предотвращения обратного траверса.
- Система должна учитывать дорожные ограничения поворотов (turn restrictions типов `no_left_turn`, `no_right_turn`, `no_u_turn`, `only_straight_on`).

**FR-3. Генерация векторных тайлов**
- Система должна генерировать векторные тайлы формата Mapbox Vector Tiles (MVT) для произвольного уровня масштабирования и тайловых координат.
- Векторные тайлы должны содержать слой `roads` с геометрией дорожных сегментов и атрибутами `highway`, `name`, `oneway`.
- Система должна применять упрощение геометрии функцией `ST_Simplify` с адаптивной толерантностью в зависимости от уровня масштабирования.

**FR-4. Поиск маршрутов**
- Система должна предоставлять API для построения маршрута между двумя точками, заданными географическими координатами (широта, долгота).
- Система должна поддерживать поиск k-кратчайших путей (до 5 альтернативных маршрутов).
- Система должна возвращать для каждого маршрута: последовательность рёбер графа, геометрию маршрута в формате GeoJSON LineString, общую длину маршрута (метры), оценку времени прохождения (секунды).
- Система должна учитывать текущую загрузку рёбер графа при расчёте стоимости маршрута.

**FR-5. Динамическое обновление загрузки графа**
- Система должна предоставлять механизм обновления текущей загрузки рёбер графа (`current_load`) для моделирования транспортных потоков.
- Система должна автоматически пересчитывать стоимость рёбер графа (`cost`, `reverse_cost`) при изменении загрузки средствами триггеров PostgreSQL.

**FR-6. Визуализация карты и маршрутов**
- Графический клиент должен отображать векторную карту с возможностью масштабирования, панорамирования, поворота.
- Графический клиент должен обеспечивать интерактивный выбор точек старта и финиша маршрута кликом мыши по карте.
- Графический клиент должен отображать найденные маршруты поверх карты с визуальным различием альтернативных вариантов (цвет, толщина линии).
- Графический клиент должен отображать информационную панель с характеристиками маршрута (длина, время, количество рёбер).

### 1.4.2 Нефункциональные требования

**NFR-1. Производительность**
- Время построения графа дорожной сети для региона moscow_center (bbox ~0.19° × 0.10°, ~45 тыс. дорожных путей) не должно превышать 120 секунд.
- Время выполнения запроса маршрутизации `pgr_KSP` с параметром `k=3` между произвольными точками в графе не должно превышать 1 секунды.
- Время генерации векторного тайла функцией `ST_AsMVT` для уровня масштабирования z=14 не должно превышать 100 миллисекунд.

**NFR-2. Масштабируемость**
- Система должна обеспечивать хранение графа дорожной сети размером до 1 млн узлов и 2 млн рёбер.
- Система должна поддерживать одновременную обработку до 10 запросов маршрутизации без деградации производительности.

**NFR-3. Надёжность**
- Система должна корректно обрабатывать ошибки соединения с Overpass API (таймауты, HTTP 429 Too Many Requests) с автоматическим переключением на альтернативные серверы.
- Система должна обеспечивать консистентность данных графа при сбоях во время построения (откат транзакции PostgreSQL).

**NFR-4. Поддерживаемость**
- Все компоненты системы должны быть контейнеризованы средствами Docker с декларативным описанием конфигурации в `docker-compose.yml`.
- Система должна использовать единую библиотеку структурированного логирования Loguru для всех сервисов.
- Логи должны сохраняться в формате JSON Lines (`.jsonl`) для автоматической индексации средствами Grafana Loki.

**NFR-5. Конфигурируемость**
- Все параметры системы (URL Overpass API, параметры подключения к БД, скоростные режимы дорог, параметры функции BPR) должны задаваться через конфигурационные файлы в формате YAML.
- Система должна поддерживать горячую перезагрузку конфигурации без перезапуска сервисов для параметров отображения карты и симуляции.

**NFR-6. Расширяемость**
- Архитектура системы должна обеспечивать возможность добавления новых алгоритмов маршрутизации без модификации существующего кода (паттерн Strategy для класса `RoutingEngine`).
- Система должна предоставлять REST API для интеграции с внешними системами мониторинга транспортных потоков.

В следующих разделах приведено детальное описание исследования структуры данных OpenStreetMap, проектирования хранилища данных, реализации программных модулей системы и результаты экспериментального исследования производительности.
