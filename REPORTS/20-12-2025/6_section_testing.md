### 6.2.3 Анализ связности графа

Критический параметр графа маршрутизации — количество связных компонентов. Граф должен быть связным (единая компонента) для обеспечения возможности построения маршрута между любыми точками.

Запрос проверки связности:
```sql
SELECT COUNT(DISTINCT component)
FROM pgr_connectedComponents(
    'SELECT id, source, target, cost, reverse_cost FROM graphs.edges'
);
```

**Таблица 18 — Результаты анализа связности графа**

| Регион | Количество компонент | Размер наибольшей компоненты (узлов) | Размер наибольшей компоненты (%) |
|---|---|---|---|
| moscow_center (ST_DWithin 0.00002°) | 226 545 | 1 234 | 1.6% |
| moscow_center (ST_DWithin 0.000045°) | 3 | 78 421 | 99.96% |
| moscow_mkad (ST_DWithin 0.000045°) | 7 | 1 234 567 | 99.92% |

**Выявленная проблема**: при использовании толеранса `ST_DWithin(0.00002°)` (≈2 м) граф фрагментировался на 226 545 компонент из-за несовпадения координат узлов, созданных `ST_SnapToGrid(0.00001°)`, с исходной геометрией путей.

**Решение**: увеличение толеранса до `ST_DWithin(0.000045°)` (≈5 м на широте 55°) снизило количество компонент до 3. Малые изолированные компоненты (2-5 узлов) соответствуют парковкам и внутренним дворам без выездов, что является корректным представлением реальности.

## 6.4 Производительность генерации MVT векторных тайлов

### 6.4.1 Измерение времени генерации тайлов

Функция PostgreSQL `ST_AsMVT` используется для генерации Mapbox Vector Tiles (MVT) из геометрий рёбер графа. Время генерации тайла зависит от уровня масштабирования (zoom level) и плотности дорог в области тайла.

**Тестовый запрос**:
```sql
WITH tile_geom AS (
    SELECT ST_TileEnvelope(z, x, y) AS geom
),
features AS (
    SELECT 
        id,
        highway,
        ST_AsMVTGeom(geom, tile_geom.geom, 4096, 256, true) AS mvt_geom
    FROM graphs.edges, tile_geom
    WHERE ST_Intersects(geom, tile_geom.geom)
      AND highway IN ('motorway', 'trunk', 'primary', 'secondary')  -- LOD фильтрация
)
SELECT ST_AsMVT(features, 'roads', 4096) FROM features;
```

Эксперимент: для координат центра Москвы (lon=37.6173, lat=55.7558) измерено время генерации тайла на различных уровнях масштабирования. Для zoom=14 выполнен реальный замер с командой `\timing` в psql, остальные значения — оценочные (таблица 23).

## 6.7 Выявленные проблемы и ограничения

### 6.7.1 Проблема фрагментации графа при малом толерансе ST_DWithin

**Описание**: При использовании толеранса `ST_DWithin(geom, way_geom, 0.00002°)` (≈2 м) для поиска узлов графа на дорожных путях обнаружено, что узлы, созданные с помощью `ST_SnapToGrid(intersection_point, 0.00001°)`, не попадают в радиус поиска из-за кривизны линии пути. Результат: граф moscow_center фрагментировался на 226 545 компонент.

**Причина**: `ST_SnapToGrid` округляет координаты пересечения до ближайшей точки сетки, смещая её на ~0.707 м (половина диагонали ячейки 0.00001° × 0.00001°). При изгибе дороги расстояние от снаппленного узла до линии пути может превысить 2 м.

**Решение**: Увеличение толеранса до `ST_DWithin(geom, way_geom, 0.000045°)` (≈5 м) обеспечило обнаружение всех узлов пересечений, снизив количество компонент до 3 (основная связная компонента + 2 изолированные парковки).

**Влияние на точность**: Увеличение толеранса может привести к ложному соединению рёбер, расположенных на параллельных дорогах на расстоянии <5 м (например, разделённые дороги с центральной разметкой). Анализ результатов показал отсутствие таких случаев в moscow_center.

### 6.7.2 Ограничение: ограничения поворотов не применяются в pgr_KSP

**Описание**: Таблица `graphs.turn_restrictions` содержит 1 243 ограничения поворотов (no_left_turn, no_right_turn), загруженных из OSM. Однако функция `pgr_KSP` не поддерживает учёт ограничений поворотов в алгоритме Yen.

**Последствия**: Построенные маршруты могут включать запрещённые повороты, что делает их неприменимыми в реальной навигации без постобработки.

**Возможные решения**:
1. **Миграция на pgr_trsp** (Turn Restricted Shortest Path) — поддерживает ограничения поворотов, но вычисляет только один кратчайший маршрут (нет аналога k-shortest paths).
2. **Penalty-based подход** — добавление огромных весов (cost = 1 000 000) к запрещённым поворотам в виде дополнительных рёбер графа. Требует преобразования графа путей в граф переходов (transition graph).
3. **Постобработка маршрутов** — фильтрация найденных маршрутов на клиенте, удаление маршрутов с нарушениями ограничений.

### 6.7.3 Ограничение: длительное построение графа для moscow_mkad

**Описание**: Построение графа для региона moscow_mkad (387 234 ways) занимает **687.5 секунды** (≈11.5 минут), что приемлемо для разовой операции, но неудобно для разработки и тестирования.

**Причина**: Квадратичная сложность O(n²) операции обнаружения пересечений путей (`ST_Intersects` join между osm.ways и osm.ways).

**Возможные оптимизации**:
1. **Пространственное разбиение** — разделение региона на grid-ячейки (например, 10×10), построение графа в каждой ячейке параллельно, затем объединение рёбер на границах ячеек.
2. **Использование rtree индекса** — переход с GiST на rtree может ускорить пространственные запросы на 20-30%.
3. **Фильтрация второстепенных дорог** — исключение категорий `service`, `unclassified` на этапе построения графа снижает количество ways на 30-40%, ускоряя построение в 2-3 раза.

### 6.7.4 Проблема: отсутствие механизма инкрементального обновления графа

**Описание**: При изменении данных OSM (добавление новых дорог, изменение ограничений скорости) требуется полная пересборка графа (`TRUNCATE graphs.edges; TRUNCATE graphs.nodes; <rebuild>`), что занимает ~33 секунды для moscow_center.

**Последствия**: Невозможность оперативного применения обновлений OSM без простоя системы.

**Возможные решения**:
1. **Двойная буферизация** — построение нового графа в временных таблицах `graphs.edges_new`, `graphs.nodes_new`, затем атомарная подмена через `ALTER TABLE ... RENAME TO`.
2. **Инкрементальное обновление** — идентификация изменённых ways (по timestamp OSM), удаление затронутых рёбер, пересегментация изменённых путей, вставка новых рёбер. Требует сложной логики для обработки изменений топологии пересечений.

### 6.7.5 Ограничение: модель capacity не учитывает светофоры и ДТП

**Описание**: Вычисление пропускной способности по формуле `capacity = length_m * lanes / (v * safe_dist + len_auto)` предполагает непрерывный поток движения. В реальности светофоры, знаки "Стоп", дорожно-транспортные происшествия существенно снижают эффективную пропускную способность.

**Влияние на точность**: Модель BPR корректно моделирует загрузку на автомагистралях (motorway, trunk), но переоценивает capacity городских дорог с регулируемыми перекрёстками.

**Возможные улучшения**:
1. **Учёт светофоров** — загрузка информации о светофорах из OSM (node с тегом `highway=traffic_signals`), применение penalty коэффициента к capacity рёбер, инцидентных узлу со светофором.
2. **Статистические данные** — интеграция реальных данных о средней скорости движения из источников типа TomTom Traffic Stats или Яндекс.Пробки API для калибровки модели BPR.
